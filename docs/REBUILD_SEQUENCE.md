# 华伴 V1.1 重建顺序

## 先做什么

先建 V1.1 新 Supabase 数据底座。

原因：

- 用户端、后台、官网管理、AI 指令、积分、供给侧都需要同一个真实主库。
- 原系统数据已经有价值，不能让新项目直接写原库。
- 新项目必须先有自己的表结构，后面才能做只读审计、快照迁移和线上测试。

## 三库边界

1. V1.1 新库
   - 新项目主库。
   - 使用 `SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY`、`TENANT_ID`。
   - 用户端和后台正式写入都走这里。

2. 原华伴库
   - 只读审计和迁移来源。
   - 使用 `LEGACY_SUPABASE_URL`、`LEGACY_SUPABASE_SERVICE_ROLE_KEY`、`LEGACY_TENANT_ID`。
   - 只能给 `/api/v1/admin/live-audit` 和迁移脚本读取。
   - 不允许新项目用户端写入原库。

3. 本地模拟数据
   - 只用于无 Supabase 时的界面预览。
   - 文件：`data/dev-state.json`。
   - 后台必须显示为本地测试数据，不得当成真实业务数据。

## 执行顺序

1. 在新 Supabase 项目运行 `db/v1_1_bootstrap.sql`。
2. 在 Vercel 配置 V1.1 新库环境变量。
3. 在本地或后台配置原库只读环境变量，跑 `/api/v1/admin/live-audit`。
4. 对齐原库审计数字：6 个测试用户、身份码、推荐关系、积分、供给侧数量。
5. 写迁移脚本，把原库数据快照导入 V1.1 新表。
6. 用户端和后台改为读写 V1.1 新库。
7. 全场景测试通过后再部署 Vercel。

## 当前判断

当前 V1.1 还不能确认真实用户关系和积分已经夯实，因为它尚未接入 V1.1 新库，也没有拿到原库只读 key 完成审计。
